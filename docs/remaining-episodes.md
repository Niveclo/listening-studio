## 性能诊断与优化

任务过程中，按用户反馈检查 CPU 与 GPU 占用，并对真实字幕画面采集 ONNX Runtime 算子记录。
检测模型的采样算子记录均由 DirectML 执行；识别模型只记录到少量 CPU 算子，其累计耗时远低于 DirectML。
这不是整套 OCR 回退到 CPU 的情况。

实际发现检测预处理会产生大型 float64 临时数组，再转回模型需要的 float32。
在项目自己的 `subtitle_ocr/engine.py` 中加入紧凑预处理适配，保留原检测尺寸与参数。
适配最终使用原运算预先计算全部 256 种 uint8 像素值的 float32 结果，并逐通道同值查表；其他输入类型使用原实现。
诊断画面的完整输入张量、识别文本、文字框及置信度与原流程相同。
同一画面、原任务同时运行时，局部测量约从 193 ms/帧降至 123 ms/帧（约 1.56 倍），不代表整集速度保证。
进一步使用同值查表后，在四路提取同时运行的另一组局部测量中，比第一版紧凑处理又快约 1.41 倍；完整输入张量与识别输出仍相同。

用户提出增加第五路后，对四路和五路各进行了约 23 秒的实际提取采样：

| 4          | 26.56 帧/秒 | 73.9%         | 50.4%                   | 6065 MB      |
| 5          | 27.42 帧/秒 | 82.6%         | 53.0%                   | 4617 MB      |

GPU 数据为 Windows GPU Engine 计数器中 3D 引擎占用之和，不是模型的纯计算时间。
片段内容及系统负载不同，短时采样不构成严格基准；第五路约 3% 的吞吐增益不明显，因此恢复四路，
